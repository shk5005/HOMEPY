# 코드 작성 전 PRD 작성 절차 (질의응답 기반)

- 문서 기준일: 2026-09-07
- 최종 갱신: 2026-09-07 16:55 (KST)
- 적용 대상: 신규 기능/신규 서비스 개발 착수 전 단계

---

## 0. 이 절차의 목적과 한계

**목적**: 코드 착수 전에 "구현자가 임의로 채워 넣을 빈칸"을 제거한다.
PRD의 품질 지표는 문장의 완성도가 아니라 **결정되지 않은 채 남은 항목의 수(Open Questions)** 다.

**전제(반드시 검증할 것)**
- 전제 A: "PRD를 먼저 쓰면 재작업이 줄어든다" → 부분적으로 사실. 요구사항 변동성이 낮고 구현 비용이 클 때만 성립.
- 전제 B: "질문을 많이 할수록 PRD가 정확해진다" → 잘못된 전제. 질문 20개를 넘기면 응답 성실도가 급락하고 오히려 오답이 문서에 고착된다.
- 전제 C: "AI가 질문을 잘 뽑는다" → 불확실. LLM의 질문은 흔한 CRUD 웹앱 사전분포에 편향된다. 도메인 특수 제약(공공 API 쿼터, 실거래 신고 lag 등)은 사람이 직접 주입해야 한다.

**이 절차를 쓰지 말아야 하는 경우 (Kill Switch)**
1. 1~2시간 내 프로토타입으로 검증 가능한 범위 → PRD 대신 즉시 코딩 후 폐기(spike)
2. 외부 규격(API 스펙, 법령, 공고문)이 요구사항을 이미 확정 → 규격 문서가 PRD를 대체
3. 사용자가 1인이고 그 1인이 개발자 본인 → 경량 체크리스트(S1·S3·S7만)로 축소

## 1. 데이터 무결성 라벨 (전 단계 공통)

PRD의 모든 문장에 아래 라벨을 붙인다. 라벨 없는 문장은 리뷰에서 반려한다.

| 라벨 | 의미 | 처리 |
|---|---|---|
| `[확인]` | 사용자 답변 또는 원문 근거 존재 | 그대로 확정 |
| `[추정]` | 기본값을 적용함. 근거는 관례/유사 사례 | 가정 대장(ASM-xx)에 등재 |
| `[미검증]` | 답변은 받았으나 근거 미확인 | 검증 태스크 생성 |
| `[확인 불가]` | 현재 정보로 결정 불가 | 미결 대장(OQ-xx)에 등재, 착수 게이트 심사 대상 |

원칙: **모르는 것을 추측으로 채우지 않는다.** 채우려면 반드시 `[추정]` + 가정 ID를 남긴다.

## 2. 전체 흐름 (7단계 + 2게이트)

```
S0 컨텍스트 캡처
   │
S1 문제 · 사용자 (Why / Who)
S2 성공 기준 (How to measure)
S3 범위 (In / Out / Non-goals)      ── G1: 방향 승인 게이트 (사람)
S4 유스케이스 → 기능 목록
S5 데이터 · 기술 제약
S6 리스크 · Red Team · 엣지케이스
S7 수용 기준(AC) · 마일스톤        ── G2: 코드 착수 게이트 (사람)
   │
   └→ 구현 시작
```

각 단계는 **질문 → 답변 → 문서 반영 → 종료조건 확인** 의 4박자로 진행한다.
종료조건을 못 채우면 다음 단계로 넘어가지 않되, **2회 재질문해도 답이 안 나오면 `[확인 불가]`로 등재하고 전진한다** (교착 방지).

---

## 3. 질문 설계 규칙

1. **한 턴에 3~5문항.** 그 이상은 응답 품질이 떨어진다.
2. **객관식 + 자유기입 병행.** 선택지는 상호배타(MECE)로 만들고, 항상 "그 외/모르겠다"를 포함한다.
3. **정보가치 테스트**: "이 질문의 답이 A냐 B냐에 따라 설계나 일정이 달라지는가?" 아니면 질문하지 않는다. 대신 기본값을 적용하고 `[추정]`으로 표기한다.
4. **되묻기 금지 목록**: 사용자가 이미 답한 것, 코드에서 확인 가능한 것, 관례로 정해진 것(로그 포맷 등)은 묻지 않는다.
5. **한 질문 = 한 결정.** "언제까지, 누가, 어떤 방식으로?"처럼 3개를 묶지 않는다.
6. **"모르겠다"는 1급 응답이다.** 실패가 아니라 OQ 등재 신호로 처리한다.
7. 각 질문에 **기본값(default)** 을 미리 제시한다. 사용자가 침묵해도 진행 가능하도록.

## 4. 단계별 상세

### S0. 컨텍스트 캡처 (질문 없음, 5분)
사용자의 최초 요청을 **한 문장 문제 정의**로 압축해 되돌려주고 승인만 받는다.
- 산출: `"[누가] 가 [어떤 상황]에서 [무엇]을 못 해서 [어떤 손실]을 본다."`
- 종료조건: 사용자가 이 한 문장에 동의 또는 수정.
- 실패 신호: 이 문장을 못 쓰겠다면, 그것은 문제가 아니라 **해법 아이디어**를 요청받은 것이다. S1에서 문제로 역산해야 한다.

### S1. 문제 · 사용자
질문 예:
1. 이 기능이 없을 때 지금은 어떻게 처리하고 있습니까? (현행 대체 수단)
2. 주 사용자는 누구입니까? (a 본인 단독 / b 팀 내부 / c 외부 고객 / d 미정)
3. 사용 빈도는? (a 상시 / b 주 단위 / c 월 단위 / d 1회성)
4. 이 기능이 실패해도 되는 정도는? (a 치명적 / b 불편 / c 무관)

- 종료조건: 사용자 1명 이상이 구체적으로 지목되고, 현행 대체 수단이 기술됨.
- 함정: "모든 사용자"라는 답은 답이 아니다. 1차 타깃 1명으로 좁힌다.

### S2. 성공 기준
질문 예:
1. 출시 후 무엇을 보면 "성공"이라 판단합니까? 숫자로 표현하면?
2. 그 숫자의 현재 기준선(baseline)은 얼마입니까? 없다면 "없음"이라 답해 주십시오.
3. 반대로 무엇을 보면 "실패"로 되돌리겠습니까? (Kill Switch)
4. 측정 데이터는 어디서 나옵니까? (로그 / 수기 / 외부 API / 측정 불가)

- 종료조건: 지표 1~3개, 각 지표에 기준선 또는 `없음[확인 불가]` 표기, Kill Switch 1개.
- 비판점: 기준선 없는 목표치는 검증 불가능한 희망이다. "월 사용자 1000명"은 baseline 없이는 의미 없다.

### S3. 범위 (In / Out / Non-goals)
질문 예:
1. 이번 버전에 **반드시** 들어가야 하는 것 3개만 꼽는다면?
2. 넣고 싶지만 **이번엔 빼도 되는** 것은?
3. 명시적으로 **하지 않을 것**(Non-goal)은? (예: 모바일 대응 안 함)
4. 마감 제약이 있습니까? (있다면 날짜와 그 날짜가 고정된 이유)

- 종료조건: Non-goals 최소 3항목. Non-goals가 비어 있는 PRD는 범위가 정의되지 않은 것이다.
- **G1 게이트**: 여기서 사람이 "방향 승인 / 수정 / 중단"을 명시적으로 선언한다.

### S4. 유스케이스 → 기능 목록
질문 예:
1. 대표 시나리오를 사용자 입장의 3~7단계로 서술해 주십시오.
2. 입력은 무엇이고 출력은 무엇입니까? 출력의 형식은? (화면 / 파일 / API 응답)
3. 잘못된 입력이 들어오면 어떻게 되어야 합니까?
4. 동시에 여러 명이 쓰는 상황이 있습니까?

- 산출: 유스케이스별로 기능 ID(F-01…) 부여, 각 기능에 MoSCoW(Must/Should/Could/Won't) 태깅.
- 종료조건: 모든 Must 기능이 최소 1개 유스케이스에 연결됨. 연결 안 되는 기능은 삭제 후보다.

### S5. 데이터 · 기술 제약
도메인 특수 질문이 누락되기 쉬운 구간이다. 반드시 아래를 묻는다.
1. 데이터 출처는? 공식 API / 크롤링 / 수기 입력 / 내부 DB?
2. 갱신 주기와 **시차(lag)** 는? (예: 실거래가는 계약일 대비 신고까지 최대 30일 지연)
3. 호출 한도·요금·이용약관 제약은? (쿼터 초과 시 동작 정의 필요)
4. 개인정보/민감정보가 포함됩니까?
5. 데이터가 비어 있거나 틀렸을 때의 표시 규칙은? (0으로 표기 금지, "확인 불가"로 표기 등)
6. 실행 환경 제약은? (로컬 / 서버 / 오프라인 / 브라우저)

- 종료조건: 모든 데이터 항목에 (출처, 주기, lag, 결측 처리) 4필드가 채워짐.
- 비판점: 이 단계를 건너뛰면 코드 작성 후반에 **데이터가 없어서 기능 자체가 성립 불가**한 상황이 발생한다. 재작업 비용이 가장 큰 구간이다.

### S6. 리스크 · Red Team
자기 PRD를 공격한다.
1. 이 PRD가 틀렸다면 가장 큰 이유는 무엇인가?
2. 사용자가 이 기능을 안 쓴다면 그 이유는?
3. 가장 먼저 깨질 가정(ASM)은 무엇인가?
4. 최악의 경우(데이터 원천 중단, 약관 변경, 비용 폭증)에 무엇을 하는가?
5. 인지 편향 점검: 확증편향(원하는 결론에 맞춰 범위를 짰는가), 계획오류(일정이 낙관인가), 매몰비용(이미 쓴 시간 때문에 진행하는가).

- 산출: 리스크별 (발생조건 / 영향 / 선행지표 / 대응) 4필드.
- 종료조건: 리스크 3개 이상, 그중 최소 1개는 "이 프로젝트를 중단해야 하는 조건".

### S7. 수용 기준 · 마일스톤
1. 각 Must 기능에 대해 "이렇게 동작하면 완료"를 Given/When/Then으로 쓴다.
2. 마일스톤은 **동작하는 최소 산출물** 단위로 쪼갠다(문서·설계는 마일스톤이 아니다).
3. 테스트 방법(수동/자동)과 테스트 데이터 출처를 지정한다.

- **G2 코드 착수 게이트** 통과 조건:
  - [ ] Must 기능 전부에 AC가 있다
  - [ ] Open Question 중 **Must 기능을 막는 것이 0건**이다 (Should 이하를 막는 OQ는 허용)
  - [ ] 데이터 출처가 실제로 접근 가능함을 1건 이상 실증했다 (샘플 호출 성공)
  - [ ] Non-goals가 명시되어 있다
  - [ ] 성공 지표와 Kill Switch가 있다
  - 하나라도 미충족 → 착수 금지 또는 범위 축소 후 재심사

## 5. 진행 중 관리 대장

- `OPEN-QUESTIONS.md` : OQ-01 형식. (질문 / 막는 기능 / 기한 / 담당 / 상태)
- 가정 대장 ASM-01 : (가정 내용 / 근거 / 틀렸을 때 영향 / 검증 방법)
- 결정 로그 DEC-01 : (결정 / 날짜 / 선택하지 않은 대안 / 이유) — 나중에 "왜 이렇게 했지"를 막는다.

## 7. 신뢰도 및 근거 수준

- 본 절차의 단계 구성은 일반적인 제품기획 실무(문제 정의 → 지표 → 범위 → 요구사항 → 수용 기준)의 통상 구조에 기반한다. `[추정]`
- "질문 20개 이후 응답 품질 저하", "턴당 3~5문항" 등의 수치는 **실측 근거가 없는 운영 휴리스틱**이다. `[추정]` — 사용해 보며 본인 데이터로 교정할 것.
- 특정 조직의 PRD 성과 개선 효과를 주장하는 정량 수치는 본 문서에 포함하지 않는다. `[확인 불가]`
- 판단 신뢰도: **Medium**. 절차의 구조는 견고하나, 효과는 프로젝트의 요구사항 변동성에 따라 크게 달라진다.
